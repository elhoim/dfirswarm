### Security: regkv, shellbags and amcache_apps withhold names, paths and data by shape (windows-forensics)

`regkv`, `shellbags` and `amcache_apps` printed key names, value names and data, shell item names and Amcache paths and hashes whole whatever they held (100% for every shape in the review's canary harness), and `regkv` withheld only by value name and place. Stacked on the pull request that bounds their lists.

- **One boundary on every way out.** A shared `BOUNDARY` block (the owner-approved hybrid: an allow-list for identifier-shaped fields, a deny-list for free text, an independent backstop) judges every key and value of an answer, of an error answer, and of every row of every file the tool writes. A name, path, key or URL is shown as it is only when it fits a plain grammar (a path component by component; GUIDs, SIDs, addresses, 0x numbers, times and hexadecimal ids up to 24 digits are plain); free text has token-shaped runs, user-info, the value after a secret's name, vendor-prefixed tokens, padded base64 and PEM keys withheld, on a copy with invisible characters taken out; a second check, written apart from both, reads it back, and a string it replaces makes a complete answer `partial` and is listed under `boundary.replaced_at`. A withheld text is `<withheld N characters: reason>`.
- **Slots.** Registry key names and paths are keys, value names are keys (many are paths), value data is free text, binary data is hexadecimal (decoded and judged by its printable text), shell item names and Amcache paths are paths, Amcache hashes are digests. The existing name-and-place withholding of `regkv` (SAM, LSA secrets, `Password*` values) is unchanged and runs first. The names of a missing key's siblings are listed in the hive's order, no longer sorted by their text.
- `shellbags` matches `contains` against the shown path, and its result file names never depended on the needle.
- **`write_values: true`** writes the originals of everything withheld to `<tool>-values.jsonl` (mode 0600, created first, never replaced). It is accepted only in a job the harness runs as secret output: the manifest declares `secret_output: {"when_args": [...]}` and the tool checks `SECRET_OUTPUT=1`, and it is refused as JSON anywhere else before anything is made.
- **Measured** (the same grammar and rules as the owner-approved hybrid design, here as the shared `BOUNDARY` block, after the review fixes below): 988 random plants per shape, 76 in each of 13 slots (text, host, name, path, key and URL, in a command line, a path, a key path, a URL path, query and fragment, and in XML). None printed whole, and no piece of 12 characters of one printed: prefixed tokens (GitHub, GitLab, Stripe, SendGrid, Google, npm, AWS key ids), JWT, PEM keys (one line and several), connection strings, user-info (an `@`, a `/` or a `+` inside the password, a random user of any length), NUL, zero-width and full-width splits, upper-case and glued prefixes (a GitLab token glued to hexadecimal digits too), AWS-shaped secret keys of 40 characters. Not zero, as averages with the worst single slot beside them (76 plants, so the worst slot is a noisy figure): 16, 20 and 32-byte base64 keys at most 0.1% (worst slot 1.3%); random base62 of 20 to 40 characters at most 0.4% (worst slot 2.6%); random lower-case letters of 24 8.5% (worst slot 16%, 18% in an earlier run); a 16-character base32 seed 11% (worst slot 18%). In a binary slot (a hexadecimal REG_BINARY value or table cell) the backstop decodes the hexadecimal and replaces every hex-encoded shape it claims (480 of 480 plants, on its own), but random bytes that hold no text are printed (200 of 200), and so is a hexadecimal secret written as text there (a 32-digit one in a table cell: 97%).
- **What it costs an examiner** (strings with any part withheld): 0 of 1,320 generated registry key paths, 5,200 file paths, 181 service names, 464 host names, 408 SIDs, 600 GUIDs and 1,200 typed digests; 2 of 109 registry value names (the 32-digit hash in a Chrome and an Edge autolaunch name); of 3,431 strings from real event logs (the EVTX attack-sample logs), 25: 17 of 1,040 whole event records, 7 of 313 command lines and messages, 1 of 322 path fields, all encoded PowerShell payloads, the 32-digit hash directories of the .NET native-image cache and similar.
- **Not recognised, by design, and asserted by a test so that the sentence stays true:** a plain password or passphrase, a pronounceable passphrase, a UUID-shaped key, a hexadecimal secret of up to 24 digits in a name or of any length in a binary slot, random binary data with no text in it, anything under 16 characters in a name (75% to 100% of such plants are printed). Withholding is by shape; a file whose secrets matter is read in a job run with `secret_output: true`. Strings the shape rules change that are not secrets: numbers of 19 digits or more (handles, a Chrome field-trial handle, a mojo pipe name), unlabelled hexadecimal runs of 32 digits or more (the native-image directories), and the query values of a URL in a URL slot.
- `tests/pack-windows-forensics-boundary-registry.test.ts`: 300 random canaries of 14 shapes planted in a value's data, a value name, a key name, binary data, a shell item name and an Amcache path/publisher/value name (real regipy and the stand-in), the share printed whole asserted per family, the unclaimed shapes asserted to be printed, the backstop shown to replace the shapes it claims with the sanitiser removed, the values file and its refusals, and names and data an examiner must read shown unchanged.
- The block text is the same in every tool that carries it and in the tool-library twins, and is marked `SHARED BOUNDARY` so that the shared-block work can converge it with the other withholding blocks.

- **Review fixes (the shared block, byte-equal in every tool that carries it).** An independent review found the following; each is fixed once in the block and asserted by `tests/pack-windows-forensics-boundary-block.test.ts` on every tool of this pull request that carries it.
  - *A run of backslashes took quadratic time.* The two patterns that take out escaped invisible characters retried at every backslash of a run (64,000 backslashes: 47 s; a 128 KB hive with one such value: 38 s against the tool's limit of 30 s); a lookbehind makes them linear (64,000: 0.06 s; 262,144: 0.25 s). The same scan of every pattern, with 50 repeated shapes, their pairs and ten prefixes at two sizes (5,704 combinations), found one more quadratic pattern that the new order of the layers exposed, a JWT header of unbounded length; it is bounded. The test drives 224 of those combinations and asserts the growth, not the time.
  - *Renaming many names that become one placeholder was cubic.* 6,000 random 24-character value names took 77 s and 108 MB of output; each placeholder is counted now (0.3 s in the block). The keys of a dictionary that are not text are sealed as text instead of stopping the serialiser.
  - *The report of where a replacement happened printed the withheld key.* `boundary.replaced_at[].at` was built from the raw keys, so a key the first layer had withheld came out whole whenever a value under it was replaced by the backstop (38 shapes x 480 plants: 81 whole canaries). It is built from the keys as they are shown, or from positions, and read once more by the backstop.
  - *The deny-list ran before the position and prefix rules and cut the context they need.* A random user of 16 characters or more of `user:password@host` was replaced and the password left (599 of 600 plants in a text or host slot printed it; 346 of 1,000 over six slots), and a GitLab token glued to 11 or more hexadecimal digits printed whole in 7% to 10% of the plants of every slot but names. Layer 2 now reads the string first, in every slot (0 of 1,000 for each, by the layers alone, by the backstop alone and together), and a user the deny-list replaced is still found by its placeholder.
  - *User-info with a `/` or `+` in the password* (1.2% printed overall, 5.3% in a path slot), a user over 64 characters, and a named value that goes on past `&`, `;` or `,` (`Password=abc&Jt6FUw^Q$%a` printed the tail, 2.4%): the URL form takes a password up to the last `@` that is followed by a host (not a port), and a value ends at a separator only when a `name=` follows it. Pieces of 12 or 13 characters of an AWS secret key (3.6% printed its first 16 characters), a `ya29.`, `SG.` or `AIza` token (1.0% to 1.8%) that two cuts left between them are caught by the check below.
  - *The backstop was not independent of the layers.* It read only the text the layers left, skipped every typed field, did not decode hexadecimal and took prefixes in one case. It now reads the original as well: a window of 12 characters of anything it calls secret in the original that is still in what was shown replaces the string (the words of the text itself are subtracted first); a typed field must hold the characters of its type; hexadecimal is decoded and its printable text read as text (the 480 hex-encoded plants above); the vendor prefixes are read in any case (`GHP_`, `akia`); a value that is not text, a number or a container is sealed as the text `str()` makes of it instead of reaching the serialiser; and a placeholder is only a placeholder when its reason is one of a fixed list (a string that only looks like one was invisible to both layers). The status basis of a backstop-partial answer no longer begins with `; `.
  - *Other.* The values file keeps 16-byte digests, at most 200,000, of the originals it has written, not the originals. A signal that arrives while the final answer is being written is held until it is whole, so a second JSON is not started. A PEM key in free text is withheld whole by the first layer and no longer makes the answer partial through the backstop.
  - *Throughput.* Each rule of the first layer is tried only when the text holds a character or word it cannot match without, chains shorter than 16 characters are skipped before they are judged, and the verdict of a word is remembered: the block's own benchmark (an event row with 1.3 KB of XML) went from 771 to 1,721 rows a second, 4,257 records a second for `evtx_query` against 1,462 before (25,958 without a boundary), with the same result on 60,000 file paths and 40,000 lines of source text (the strings it changes are the same).
  - *`shellbags` and `regkv`.* `shellbags` with `contains` answered `complete` with no entry when the needle was in text the boundary withheld; entries that did not match and have text withheld in their path are now counted (`contains_blind_entries`), the answer says why in `status_basis` and is `partial`. The count is the same whatever the needle is, so it is no way to test a guess. `regkv` lists the subkeys of a key in the order the hive stores them (alphabetical by the raw names), so the order of withheld names among their siblings is evidence order, not computed by the tool (documented, not changed). `regkv` with 6,000 random value names in one key answers in seconds (see the test), not in 77 s.

windows-forensics is re-sealed and raised by a patch version; the other withholding pull requests of this review also raise it, so the later ones need the merge-prep step.
