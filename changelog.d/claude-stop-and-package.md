### Fixed: a stop seals every job it ends, chains the harness's last lines, and a package's scan is linear

A long memory-case run ended with four marks against its record, each found afterwards: the stop said `stop_incomplete` for a job's worker the hub was removing at that moment, that job's staging directory was left unsealed, two of the operator's commands after the stop were left outside the trace's chain, and the package step's hygiene scan was still running after two hours at full CPU over a 4.2 GB package with one job's 1.37 GB `stderr.log`. Each is fixed where it arose.

- **No worker starts behind a stop.** From the moment `swarm.sh stop` begins (it writes `.stop` in the hub's directory first) the hub's job service starts no worker and accepts no job; what waits is cancelled on the record when the hub goes. On that run a two-hour memory job's worker was started six seconds into the stop.
- **The stop waits for the hub before it counts the VMs.** It asks the hub to go and waits for it (`SWARM_STOP_HUB_EXIT_SEC`, default 180), so the hub's job service removes the workers it runs and seals their jobs first. A job's worker still listed once the hub has gone is removed by a second finish, and the list is asked again for up to `SWARM_STOP_JOB_VM_WAIT_SEC` (default 60) before anything is called left up and the run `stop_incomplete`. A hub still up after its bound keeps its pid file and directory and the run is `stop_incomplete`: the next stop finds it, waits for it and seals after it, never beside it (`seal-left` also refuses while a hub process of the run lives, found by its command line). Both bounds take whole seconds; anything else is the default.
- **Every staging directory is sealed or accounted for.** The job service's stop asks again for each worker msb could not confirm gone (three times, two seconds apart) and seals its job once it is gone (`job_fenced` with `by: "stop"`); one still unconfirmed is named on the journal (`job_unsealed`, its staging directory and why). With the hub gone the stop runs `vm.ts seal-left`: each such job is sealed once msb says its worker is gone, as recovery would seal it (a job the hub left running as `stopped`), or its staging directory is named with why. Custody names each directory left with that why.
- **The harness's spilled trace lines are chained.** Once the run's daemons are down the stop chains the lines the collector could not take (`traces/system-spill.jsonl`, `traces/hub-spill.jsonl`: an operator's command after the collector stopped, the hub's last words, this stop's own line) with the collector's own code (`trace-collector.mjs --gather`), each written unverified and marked `gathered` with its spill and its sha256, the anchor moving with the chain. The spilled lines are kept whole in `traces/<name>.gathered.jsonl`, each once, and a package carries them; a line that is not an event, or one naming a seat (a seat's word, never chained as the harness's), stays in the spill and is counted. Custody counts the gathered lines, holds a gathered operator line to the operator's audit by the time the command ran, and does not read its chaining time as a clock off the host's. Safe to run again; refused while a collector answers.
- **The package's leak scan is linear.** It looked for every sensitive word and digest with its own search over every 32 MiB of every file; now one automaton per form (`scripts/multi-match.ts`, Aho–Corasick) reads each 8 MiB window once, whatever the number of words, with the same rules (normalised text, UTF-8, UTF-16LE and lower-case bytes, the short-word rule, digests in text, filenames). The windows overlap by twice the longest form and the context a short word is judged by, and a short word is judged only where its context is whole (a window's edge cutting the hash or number it sits in made it a false hit, which refused a redacted package; the old scanner had the same flaw at its 32 MiB edges). `HYGIENE.json`'s count of carried files hashes each file as a stream. `tests/leak-scan-linear.test.ts` holds the new scan to the old one on random packages and scans a 64 MiB log with 2,700 words and 1,600 digests within a bound the old one could not meet (about a second here; the old one took two minutes). Over that run's own 4.2 GB package, read in place, the new scan took 80 seconds.
- **`package` says when the record is not finished**: a WARN when a job's staging is unsealed or the harness's trace lines are outside the chain, with `stop` again as the fix.
- **The console marks a question must be established.** The Questions tab's add form has the field (`--must-establish`, a material question only); a question's card shows who required it (the goal, the examiner, the operator), when and why, or who released the requirement and why, and has the action that requires it or releases it with why (`amend --must-establish | --no-must-establish`, no new revision), offered only to the operator or an examiner, as the register holds it: a question's own asker can release the requirement no more than set it, and the refusal now says releasing.
