### Added: the computer-forensics-base pack applies a SQLite write-ahead log in a copy, never beside the evidence (`sqlite_snapshot`, and `sqlite_query` on its result)

`sqlite_query` opens the file it is given immutable, so a row committed only in the `-wal` was missing from every answer; it said so ("WAL NOT APPLIED") but could not do more. `sqlite_snapshot` is the missing half. It copies the set (database, `-wal`, `-shm`, `-journal`, named from the real path as SQLite looks for them) into a new directory, 0700, under `original/` (new files, 0600) while hashing them with sha256, and reads each source's size and modification time before and after: `changed_during_copy` says a live file moved under the copy, and the answer says the files were copied one after another, not at one instant. The copy of the WAL is read against the format: header magic, version 3007000, page size, the header's own checksum, then each frame's salts and its cumulative checksum in the byte order the magic gives. The receipt (`snapshot.json`, also the answer) reports the frames in the file, the frames valid, `frames_committed` (the last commit), the valid frames after it that no commit covers (never applied), and the first invalid frame with its reason: a leftover of an earlier generation (salt mismatch, a note), a damaged or torn frame (checksum mismatch) or a file that ends inside a frame (both make the snapshot `partial`). The WAL is applied by SQLite itself to a second copy (`applied/database.sqlite`: the copy and its `-wal` opened and checkpointed, the `-shm` not used); the tool compares SQLite's frame count with its own reading (`counts_agree`), counts the pages of the main file the WAL changed, and a WAL with no valid header, no committed frame or another page size is not applied, with the reason, `database` then being the copy of the main file. A last commit that claims a database larger than `max_bytes` is not applied (a hostile WAL could otherwise make SQLite build a terabyte-sized sparse file). A hot rollback journal is copied and reported and not rolled back. Nothing is overwritten (an existing `out_dir` is refused), a set larger than `max_bytes` is refused before a byte is copied, `max_seconds` ends the copy, the WAL check and SQLite's checkpoint, and SIGTERM, SIGINT and SIGHUP leave an `interrupted` receipt. Exit 0 with status `partial` when the copy was made and the WAL could not be applied or read. Not measured: deleted records, the freelist and unallocated pages (nothing here recovers them; a recovery backend is still the owner's decision), and whether a live set was consistent when copied.

`sqlite_query` (version 5) takes a snapshot's directory, or the database inside one, as `db_path`: the answer then carries `snapshot` (what the snapshot holds, and whether the file queried still matches the receipt's sha256) and `database_opened`, and `snapshot_status` says which state the rows are (the copy with the WAL applied, or the snapshot's copy of the main file with its WAL not applied). `apply_wal` is not a parameter of `sqlite_query`; asking for it is an error that names `sqlite_snapshot` (the smaller design: the query tool stays read-only and immutable, and one snapshot serves any number of queries). The existing answer fields are unchanged, and the "WAL NOT APPLIED" text now names the tool that does it. The tool-library copy follows (held equal by `tests/tool-library.test.ts`), and a new leaf, `data/sqlite`, says that a database is a set, when to run the snapshot, how to read its receipt and what it does not show (this also keeps the pack's links clean). Pack tests: `test_sqlite_snapshot.py` (27, with real WALs written by Python's `sqlite3` while a writer stays open, a big-endian WAL written from the format's checksum rule with SQLite as the judge, a damaged frame, a torn file, a bad header checksum, frames of an earlier generation, an uncommitted tail, a hostile commit size, a hot and a zeroed journal, a file that grows while it is copied, and a SIGTERM during the copy).

### Changed: `ioc_scan`, `chunk_needles` and `sig_carve` find their matches with one shared engine

The three scanners each carried their own loop for reading a stream in blocks, holding a match back until its context is in the buffer and trimming the buffer. They now carry one engine (the text between the `SHARED SCAN` markers; the pack stays standalone, so it is copied, not imported) and keep their own answers, pages, budgets and result files: `ioc_scan` and `chunk_needles` ask it for context on both sides, `sig_carve` for none, with the bytes before `start` as a prefix so that a continuation of a stopped scan finds a header that crosses the stop exactly once, and a scan that stops flushes every header wholly inside what it read. `tests/test_scan_core.py` (7) holds the three copies equal, holds the engine to a brute-force search over 1,500 random streams cut in random ways (needles that overlap and contain one another, one-byte reads, empty reads, context checked byte for byte) and over 800 stops and continuations, and holds the three tools to the same offsets for the same bytes at five read sizes (ASCII) and three (UTF-16LE); a deliberately broken engine fails them. No answer changed: every earlier test of the three passes unchanged. `ioc_scan` 5, `chunk_needles` 7 and `sig_carve` 3. The windows `utf16_urls` and memory `mem_carve` can copy the same block when their packs take it up. `tests/pack-base-shared.test.ts` also holds `sqlite_snapshot`'s withholding block equal to the network pack's.

`chunk_needles` also prints the JSON answer for an image it cannot choose (none under `inputs/`, or several) on stdout; it went to stderr as a bare `SystemExit` message. The tool-library carried a much older `chunk_needles` (version 3, which returned the bytes around a hit inline); it is now the pack's, `tests/tool-library.test.ts` holds it equal with the other five copies, and the library test that expects it to fail closed for a missing image accepts the pack's messages. `icat_extract` has the same stderr behaviour in its image resolver and is left for the next change.
