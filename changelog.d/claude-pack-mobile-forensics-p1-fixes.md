### Fixed: the mobile pack's filters and sealed files no longer answer questions about text nobody can see

`sqlite_freespace`, `manifest_db` and `protobuf_peek` withhold the text of a free page, the name of a backup file and the content of a protobuf field. Each of the following let a caller learn a withheld string one bit at a time, or printed some of its characters; they are closed, and the pack is 1.5.4.

- `sqlite_freespace` `contains` as a size and digest oracle: the values file held only the fragments the expression matched, and the harness shows a job's output size and digest to whoever asked for the job. The file was 299 bytes for the right prefix of a hidden token and 0 for a wrong one (62 calls recover a character). The file now holds a row for every fragment found, whatever the expression says; each row has `match` (1 matched or no expression, 0 did not, 2 could not be decided) and a random `run`, so its size does not depend on the expression and its digest differs in every run (ten expressions, right and wrong prefixes, one size). A reader of the file filters on `match`. The answer's `secret_values.written` is now the number of fragments, not of matches.
- `sqlite_freespace` `contains` as a timing oracle: it accepts only an expression of at most 256 steps (it was 16,384): no `*`, `+` or `{m,}`, no repeat of a choice, no lookahead, lookbehind or back reference, at most 256 characters. `\d(?:.?){10}Y` took 1.75 s on a hidden region of digits and 0.05 s on one of letters, and `Zq7K(?:.?){10}Y` was 90 times slower with the guess present; both are refused now. What is left is small per character and not zero: the slowest of 171 accepted candidate expressions (one class of characters repeated 250 times) took 0.06 s of CPU on 32,768 characters of that class against 1.1 s under the old bound. It adds up with the volume of hidden text (`\d{250}x` on 22 fragments of 60,000 characters, 1.3 MB: 1.4 s of CPU on digits against 0.16 s on letters), so the duration of the job can still say that much of the free space is of a class the expression matches, by at most the time the work budget below takes (about 7 s). The manifest, the README and the skill say so; the answer does not follow it.
- `sqlite_freespace` `contains` that ran out of time: a fragment it could not decide on was written to the values file as if it had matched while the answer said `complete` (`(?:a?){10}Z`, which matches nothing, wrote 27 of 39 rows), and the time the expression took did not count toward `max_seconds` (`max_seconds: 3` took 10.3 s). Such a fragment is marked `match: 2`, counted under `scanned.contains_not_decided` and `problems`, and the status is `partial`. The time the expression takes does not reach the status: it first counted toward `max_seconds`, and with `\d{250}x` on two databases of the same layout and `max_seconds` 0.5 the one of digits answered `partial` (1 fragment undecided, 13 pages not reached) and the one of letters `complete`, three runs in three, so one call said whether the hidden text was mostly digits. The expression now has a work budget in sizes the answer shows (one step is a fragment's characters times the expression's cost bound, at most 1,000,000,000 steps and fewer for a short `max_seconds`): a fragment that would take the run past it is `match: 2`, the same for any text of those sizes, and the clock of `max_seconds` does not run while the expression does. On the same two databases the answers are now equal at `max_seconds` 0.5, 1.0 and 1.2 (20, 18 and 18 fragments undecided, no page unreached), and the 10-second total allowance stays gone.
- `protobuf_peek` counts: for a window that was not shown, the answer still printed `field_count`, `top_level_fields`, `counts` and, for a group, the status `unsupported`. The parse stops at the first error, so those numbers came from the bytes of a token as much as the rows would have: a window slid over a base62 token left 18 of 62 candidates for each character, a digit 3.4 of 10, and a 6-digit PIN lost about 8 of 20 bits. Every window that is not shown now gets the status `not_accepted` in the same words and zero counts. Its values file is one row of the size of the window (the whole window as hexadecimal and what the parser found, in a fixed width) instead of one row per field it parsed, and the readings of a number under a nested message are written in one width.
- Recovery-password names: only the dashed eight-by-six form was withheld from a path or a domain. A name is now withheld when it holds 42 or more decimal digits with at most three characters that are neither a letter nor a digit between two digits, after NFKC folding: spaces (a run of them counts as one), underscores, dots, any dash, comma, colon, semicolon, plus, brackets, quote marks, `#`, accents, symbols, 48 contiguous digits, full-width and Arabic-Indic digits, a zero-width character inside, seven groups, and a key split across path components (the slash is such a character; each component that holds digits of it is withheld). On a seeded set, 29 shapes were withheld 40 times of 40 each, and 13 shapes that are not keys (uuids, hashes, timestamps, phone numbers, six groups of six digits, photo and dated directory paths) were printed 40 times of 40, in each of the three tools. Judging is linear and bounded: the pattern that tried every digit as a start cost 0.46 s per MB of a path or domain made of 41 digits and a letter, repeated, outside `max_seconds` (three rows of 8 MB: 7.6 s of CPU with `max_seconds` 5, 11.3 s without, and a cell of the 1 GB SQLite allows would have passed the tool's 300-second timeout). The runs are now found in one pass and only a long enough run is looked at again (a 32,768-character name costs at most 3 ms, down from 29 ms), and a path or domain over 8,192 characters is not judged but printed as `<name too long to judge withheld>` (three rows of 8 MB: 0.1 s of CPU with or without `max_seconds`).
- `manifest_db` says `partial` when a listed row's `file` cell was not read (`too_large`) or could not be used (`malformed`), and lists `domains` by the text it prints, so a withheld domain no longer stands where its hidden name sorts. `file_id`, the SHA-1 of the domain and the real path, is still printed for a withheld path, as it is the blob's name in the backup directory and a listing of the directory shows the same digest; the manifest and the skill say so.
- The three tools write their answer in one piece: a stop signal that arrives while a large answer is written to a reader that has not read yet used to leave a truncated answer followed by the failure document; the signal is ignored once the answer is being written, and the reader gets one document. A reader that takes nothing for 30 seconds is given up on (the tool exits with 141): with the signals ignored, a pipe nobody read could be ended only by SIGKILL. `[[:alpha:]]` and similar no longer print a `FutureWarning` to stderr.
- `protobuf_peek`'s residual outside the layout it was measured in is now stated: for a token that is the whole of one string field, 0 to 1.2 percent of tokens have a shown window; for a 32-character hexadecimal token split across two fields, 4.8 percent; for a 64-character one written as repeated six-byte pieces, 12.5 percent; for a 32-byte one, 8.1 percent; for a 64-character one inside a nested message, 3.9 percent (never a whole token). These are the rates at any `max_fields`. A caller-set `max_fields` had raised them: a window the field budget stopped was accepted on the fields it had read, so with `max_fields` 4 acceptance was judged on the first four fields of an aimed window, and 19.1 percent of 64-character hexadecimal tokens had a shown window (single string field), 6.0 percent of 32-character ones and 1.2 percent of 24-character base62 ones, with up to 2 percent of a token's bytes derivable. An aimed window (an `offset` or a `length`) is now shown only when the whole of it parsed: at `max_fields` 4 the same tokens give 0.9, 0.6 and 0.1 percent (1,000 tokens of each type, the same as at the default 1.0, 0.6 and 0.1; split, repeated and nested layouts at `max_fields` 4 are at or below their default rates). A window nobody aimed is still shown as far as the budget read.
- What the values files' size follows is now stated for `protobuf_peek` as it was for `sqlite_freespace`: the text of a string field is written as JSON writes it, so a quote or a backslash adds a byte and a control or non-ASCII character adds more (about log2(count+1) bits per call for a field a caller isolates with `offset` and `length`, nothing for a token of letters and digits); the time of the parse of a window that is not shown follows the number of fields read. Neither is removed: the text is written readable on purpose.
- What a requesting agent can see is stated in the manifests, the README, the skills and the packs guide: the answer, and the size and digest of the job's files. The sealed values file lies under `store/`, which an agent's VM mounts read-only, so an agent that opens it reads every row, the values and `match` included; the tools' measures guard what is shown without opening the file, not an agent that does. Whether an agent may open it is decided by the sandbox's mounts, which this change does not touch.
- `packs/mobile-forensics/tests/pack.test.sh` ran the tools as a job without `SECRET_OUTPUT=1`, so `protobuf_peek` refused `write_values` and the shell-suite step failed; it sets the flag now.

The earlier fixes of this pack stand: `contains` and `domain` of `manifest_db` match the printed path and domain; a `file` cell is read only when it is a BLOB of at most 1 MiB (three rows holding a 29 MB archive took 399 MB of resident memory and now take 22 MB); a window that is entirely printable text is never shown and a window aimed with `offset` or `length` needs 16 bytes and four fields; `sqlite_freespace` and `protobuf_peek` declare `secret_output: {"when_args": ["write_values"]}` and refuse `write_values` in a job that was not run as secret output; all three answer SIGTERM, SIGINT and SIGHUP with one JSON document (`status: failed`, `interrupted`), exit 128 plus the signal, close and name the pages already written and remove the `manifest_db` working copy; all three say `status_basis`, and `protobuf_peek` says `status`; the manifest, skill and README say that the device identifiers in the plain plists (serial number, UDID, IMEI, ICCID, phone number) are printed.

### Fixed: the tool test helpers no longer crash on a child that never reads its input

`runPy`, `runSh` and `runPySnippet` wrote their JSON to a child's stdin with no error listener, so a fixture builder that exits without reading it (every `runPySnippet` call that passes `null`) could end the whole test file with `write EPIPE` on a loaded runner. The helpers ignore the error of a child that exited (`EPIPE` and `ERR_STREAM_DESTROYED`, and no other), and `null` now means no input at all.
