### Fixed: a vm-hub test that could wait forever, and a time limit on every node test

Twice on 2026-10-01 CI's Node 24 job sat on `tests/vm-hub.test.ts` until its 20-minute limit cancelled it, with no test named and no process but the suite's own left; the same file passed on Node 22, in the Linux job and locally.

- **The directory-swap test listens for its swapper's exit from the spawn.** The test (Linux only) runs a second process that swaps a seat's directory for a link for 2.5 s while it reads for 2.5 s, then waited for that process's `exit`. The swapper's 2.5 s start once its node is up, only tens of milliseconds after the reads start theirs (measured: 9 to 95 ms on Linux, Node 22 and 24), so a last read that overran by more than that let the exit come first, and the `once("exit")` added afterwards waited for an event already gone while the hubs' open sockets kept the process alive. With the swapper made to end first on purpose, the old test never ends and the new one passes in 2.5 s. The hang did not reproduce unprompted locally (24 whole-file runs and 40 runs under CPU load in a Linux container on Node 24.21.0, 48 on macOS, where the test is skipped), so this is the cause found, not one caught in the act.
- **`npm test` runs every test under a five-minute `--test-timeout`** (`scripts/test-node.ts`), unless the caller passes its own (`npm test -- --test-timeout=N`). On Node 24 a test that waits forever fails by name after five minutes and the file goes on; Node 22 also holds each suite file to the limit and names the file. The slowest test takes about 30 s on a hosted runner and the slowest file about 75 s (ui-server, on macOS). A file whose tests all end but whose process stays up on a handle left open is not covered on Node 24; `--test-force-exit` would hide that, so it is not used. `npm run test:vm` is unchanged.
