### Security: the macOS pack's `plist_read` no longer prints a digest, a head or a verifier, and the skills stop routing account plists through an open reader

`plist_read` returned the sha256 and a base64 head of every binary value (`max_blob: 0` still returned the digest) and printed every string of a plist it read, including account plists under `dslocal/nodes/Default/users/`, which hold a password verifier (`ShadowHashData`), Kerberos keys and sometimes a hint. The worker prompt forbids a hash of a secret anywhere. It now follows the secret-safe output pattern of `recovery_key_scan` (`docs/packs.md`, "Secrets and sensitive output"): a binary value is its length and kind; a value under a key whose name marks it secret-bearing (verifier, Kerberos keys, password, passphrase, secret, token, credential, private key, hint) is withheld at any depth and when `key` selects it; each is a locator (finding id, key path, kind, length). `write_values: true` writes the values to `$OUT/plist-values.jsonl` (mode 0600, created before anything is read, an existing file or link refused), only when the tool runs as a job, a binary value as base64 up to `max_blob` bytes with its whole length beside it; outside a job it refuses and writes nothing. `triage/system-profile`, `artifacts/plists` and `accounts/users` say an account plist is read as a `secret_output` job or by `key` selection, carry a Sensitive output line, and write a verifier as where it sits and how long it is. `accounts/users` no longer says a screen state, a focus record and an authentication put a person at the keyboard, that Remote Login with an authorized key makes a Mac reachable by whoever holds the key, or that the file's modification time is the date to quote; `artifacts/knowledgec` no longer says three screen and focus records are a person at the keyboard.

### Fixed: the macOS pack's tools stop turning failures into clean results

- **`fsevents_parse`** returned no records and no problems for a `3SLD` page or a file that is not an FSEvents record file, ended a file silently at a gzip member that did not decode, clamped a bad page length to the rest of the data, skipped bytes between pages and dropped an incomplete record without a count, skipped `fseventsd-uuid`, held the whole file inflated with no bound, and its note called a `Renamed` record a move against its skill's own warning that a rename gives no pair. Per file the state is parsed, partial, empty, unsupported or failed; per gzip member complete, truncated or failed with its compressed offset; per page parsed, unsupported, invalid length or truncated; per record decoded, empty path or incomplete; skipped bytes are counted and located; a flag bit with no name is `flags_undecoded`; the exit is non-zero when nothing was decoded. Only `1SLD` and `2SLD` are read and the manifest says so. Decoding is streamed, expansion capped (`max_expanded_bytes`, `max_page_bytes`), records written as they are decoded, each carrying its member, page and record offsets, and an `out_file` is not overwritten.
- **`knowledgec_query`** read `ZOBJECT` only, though its manifest and skill said it joined `ZSTRUCTUREDMETADATA` and `ZSOURCE`; it never exported `ZVALUEINTEGER` or `ZVALUEDOUBLE` (so `/device/isLocked` and `/display/isBacklit` could not be decoded from its output), dropped the row id and UUID, ignored `since` and `until` on a database with no `ZSTARTDATE`, listed the thirty most numerous streams without saying so, put an unescaped path in a `file:` URI, and opened a database with a `-wal` beside it read-only in place (a failure reported as "not a SQLite database" on a read-only directory, a new `-shm` beside the evidence on a writable one). Entries now carry the `Z_PK`, the typed values, the raw and converted times, and every non-null column of the joined metadata and source rows, joined from the schema the file has, with a fingerprint of the three tables' columns; with a WAL or a hot journal the files are copied to a private directory, SQLite applies them there, the frames applied are counted and the copy is removed; every stream is inventoried; an unapplied filter is `filters_unapplied` and the answer is partial.
- **`unified_log`** reported `complete` with zero entries for a reader that exited 0 and wrote no file, stopped counting unparsed lines once its inline preview was full (the Linux branch never parsed), copied the `/private/var/db` trees with their links, no budget and the second tree overwriting the first, overwrote an earlier run's output, did not clamp its timeout to its manifest's limit and did not declare `unifiedlog_iterator`. `status` is now failed, empty, partial or complete and says it is about the run: `decoded_coverage` counts the whole output (lines, JSON records, entries, lines that are not records, records with none of an entry's fields) and `support_files` is a census of what the input holds. Staging is counted, bounded and refuses a link, a special file and a member in both trees with different bytes; `out_dir` may not hold an earlier run's output; the timeout is clamped and an overrun leaves a partial receipt; the reader's version is recorded.
- **`plist_read`** also read every file into memory before writing any, recursed without a bound (a plist nested 5000 deep ended the sweep with a traceback), followed a link in a directory, overwrote an `out_file`, and labelled a working copy's mtime as `modified`. It reads one file at a time (a file that does not parse, or is over `max_file_bytes`, `max_nodes` or `max_depth`, is that file's row; files not reached before `max_seconds` are counted and named), sorts the walk, does not follow links, refuses an existing `out_file` and says `extracted_file_mtime`.

### Changed: the macOS pack's skills say what each artefact shows, what it does not and what corroborates it

All eight skills are rewritten or revised in the defender's voice. `artifacts/fsevents` says what the parser read, that an event id orders and does not date, and that a dated path does not date its neighbours; `artifacts/knowledgec` stops saying the tool joins what it did not, separates device state from presence, and says a WAL is rows; `filesystem/apfs` no longer says APFS leaves no record or that precision is accuracy, asks for a snapshot enumeration and a coverage statement, keeps Core Storage and encrypted APFS apart and says `fvdeinfo` is not assumed to read APFS; `logs/unified` says the unified log is not an exhaustive execution or authentication record, adds timesync and boot identity and separates the two readers; `persistence/mechanisms` stops saying a daemon runs as root at boot and an agent at login, and no longer mixes a system extension's approval, a TCC row's modified time or Accessibility with a grant time or SYSTEM; `triage/system-profile` names `ProductBuildVersion`, says the zone applies only to local civil time, and names `mac_apt.py` (installed in the amd64 worker image only). The index drops "nobody turns off", "prove it happened", "what a person was doing" and "true times". The goal template's questions 1, 3, 4, 5 and 6 say what the evidence can support (no grant times without further evidence, no person at the keyboard); its minimum of eight ledger events is left for the owner. `requires/host.json` drops the claim that Apple's reader is the only one that resolves format strings properly, says `mac_apt.py` is amd64-only and untested here for the inputs the project lists, and drops the brew route that installed a Python binding for `fsapfsinfo`. Every skill names the tools and programs its front matter lists and the other way round, so the pack leaves `tests/pack-links.pending`. A new suite, `tests/pack-macos-forensics.test.ts`, builds its fixtures from Apple's binary property list layout, the FSEvents page layout and Core Data's knowledgeC schema, 36 of its 38 cases failing on the old tools (one runs on macOS only) (the other two check the fixture itself and that a file that is not a knowledgeC database is still refused).

Output fields that changed, for anything that reads these tools' answers: `plist_read`'s `modified` is `extracted_file_mtime` and a binary value no longer carries `_sha256` or `_base64_head` (it is `{_binary_bytes, _kind, finding_id}`); it exits 1, with its whole answer, when no matched file could be read (it used to exit 0 with the error inside the file's row). `knowledgec_query`'s `value` is `value_string` (beside `value_integer`, `value_double` and `value_type_code`), its `bundle` is gone (it was the value string again), and `streams_in_database` (a map of the top thirty) is `streams` (a list of every stream). `fsevents_parse` exits 1, with its whole answer, when it decoded nothing (every file unsupported or failed). `unified_log`'s `status` has two more values, `empty` and (for a reader that exits 0 and writes no file) `failed`, and its `timeout_seconds` floor is 1 second.
