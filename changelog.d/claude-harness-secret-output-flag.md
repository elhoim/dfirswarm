### Added: a tool's manifest can declare that its jobs are secret output, and a secret job's process is told

A tool manifest may carry `"secret_output": "required"` (every job of the tool) or `"secret_output": {"when_args": ["write_values"]}` (a job that sets one of the named parameters, each one of the tool's own `params`, declared `type: "boolean"` with no default that is on; anything but an absent, null or false value counts as set, since the harness applies no defaults). The job service reads it where it checks the tool. A job it applies to is run as if the agent had given `secret_output: true`, whether the agent did or not (an agent's `false` does not turn it off): its outputs are sealed sensitive, a job reading them is derived, an entry citing them is recorded sensitive and a redacted package withholds them. The job's spec records `secret_output_by: "tool_manifest"`, its `sensitive` record says `declared: "tool_manifest"`, and the answer to the agent carries the same `secret_output_by`. A declaration the service cannot read refuses the job with the rule it breaks, and `scripts/pack.sh seal` validates the same key; a tool an agent forges with `make_tool` has none, and the agent's flag decides for it, as before (and `make_tool` never rewrites a tool that came from a pack or carries the key). The key is for `kind: tool` jobs: a recipe, including a forged tool that declares the recipe protocol, that carries it is refused, and the seal refuses it in `recipe.json`. `pack.sh adopt` keeps `secret_output`, `use` and `requires`. Nothing in the harness names a tool or a format: it reads one key and whether a named argument is set.

The process of a job run as secret output (by the agent's flag, a manifest or a command job given the flag) now has `SECRET_OUTPUT=1` in its environment, and every other job has it unset, so a tool that offers a values mode can refuse it in a job that is not secret. The variable is a signal to a tool that behaves, not a boundary: a command job is code the harness does not read, and can set `SECRET_OUTPUT=1` for itself.

### Changed: `sqlite_query` and `recovery_key_scan` declare it and check it

Both declare `{"when_args": ["write_values"]}`, so a job that sets `write_values` is secret output without the agent's flag. Both refuse `write_values` in a job whose process lacks `SECRET_OUTPUT=1` (a command job that runs the script by hand, or a harness that does not set it) as JSON, with `write_values: "refused"` and `written: false`, before anything is opened or created; the refusal outside a job is unchanged. The other tools that write values to a file (those with a `write_values` or similar parameter, in every pack) are not changed here: they are held by the agent's flag and their skills' line until they adopt the same key and check. `sqlite_query` is version 7 and its tool-library copy is updated with it. Packs `computer-forensics-base` and `encrypted-containers`; `docs/packs.md` (section 8) and `docs/protocol.md` describe the key and the variable.
