### Added: the base pack has a router, so a run that carries it with other packs stays inside the skills index budget

`computer-forensics-base` names `base/router` (at most 400 tokens) as its router. When a run's index is over its 2,500-token budget the prompt shows each router-bearing pack by its router's one line, and the router names every other base skill by the question it answers. The `disk` profile (base, encrypted-containers, windows-forensics) had 3,058 tokens of index entries and no pack to shorten; it now shows 2,194. Combinations that still exceed the budget (base with windows-forensics and linux-forensics or memory-forensics, and some sets of four packs) do so because windows-forensics, linux-forensics, memory-forensics and macos-forensics have no router: a pack with none is shown whole. Pack `computer-forensics-base`.

### Added: `sqlite_query` can write the values of a secret table to a sealed file

With `write_values: true`, in a job run with `secret_output: true`, the tool takes `table` (and optionally `columns`, `rowid_from`, `rowid_to`) instead of `sql`, writes every non-NULL cell to `sqlite-query-values.jsonl` under `$OUT` and puts none of them in the answer. The file is mode 0600, created with `O_EXCL` and `O_NOFOLLOW` once the table is found and before its first row (a wrong table name or a file that is not SQLite leaves nothing, and the same job can ask again; a second export in one job is refused as JSON and a link at the name is not followed), and it ends with an end line, so a file cut short by a kill or a full disk is recognisable. The answer carries each cell as `type:length`, per-column counts and the first rows; `locators_file` has every row, always (bounded at 2 GiB, said). No hash, digest or fragment of a value is written anywhere, and a database, table or column name shaped like a token is withheld from every printed channel (the network pack's withholding block, now also in this tool, byte for byte; the test that holds the copies equal covers it).

There is no `sql` in this mode on purpose: a `WHERE` or `LIKE` over a column whose values are withheld would confirm a guess, one call at a time, so the mode exports whole rows, reads them from the table itself and never through an index (whose order is the indexed values'), and takes no filter. What locates a row is said as `table_kind`. On an ordinary rowid table it is the `rowid`, SQLite's row key, which is no column's value unless the application set it, and `rowid_from`/`rowid_to` select by it. On a table whose one primary key column is declared `INTEGER`, that column is the rowid, so the rowid is a value: it is never printed, a range is refused (`rowid_is_a_value`), and rows are located by their position `n`, which ranks the key's values; on a WITHOUT ROWID table `n` follows the primary key and ranks its values too. A virtual table is located by `n`; where its module cannot start under the read-only authorizer (fts5 on Debian's SQLite 3.40) the answer is the named state `virtual_table_unsupported`. A number's length is the characters of its decimal form, so it tells the number's order of magnitude.

sqlite's own error message is never printed in this mode (a generated column's `json_extract` quotes the value it failed on): the answer gives the error's class and the row, and the message goes to the values file. A row that cannot be read whole is read a cell at a time: a cell over the 64 MiB length limit (`value_too_large`) or one SQLite cannot compute (`unreadable`) is listed in `cells_not_exported` and the rest is exported. A write that fails (a full disk) ends the export as JSON with `values_file_error`, the whole lines the kept file holds and `complete: false`, exit 0. Outside a job the request is refused as JSON before anything is opened; the ordinary mode is unchanged. `data/sqlite-secrets` says all of this and keeps the locator-column query as the fallback outside a job; `docs/packs.md` states the rule for every tool that takes a filter. The tool-library copy is updated with it. Pack `computer-forensics-base`.
