### Added: `sqlite_query` can write the values of a secret table to a sealed file

With `write_values: true`, in a job run with `secret_output: true`, the tool takes `table` (and optionally `columns`, `rowid_from`, `rowid_to`) instead of `sql`, writes every non-NULL cell to `sqlite-query-values.jsonl` under `$OUT` and puts none of them in the answer. The file is mode 0600, created with `O_EXCL` and `O_NOFOLLOW` once the table is found and before its first row (a wrong table name or a file that is not SQLite leaves nothing, and the same job can ask again; a second export in one job is refused as JSON and a link at the name is not followed), and it ends with an end line, so a file cut short by a kill or a full disk is recognisable. The answer carries each cell as `type:length`, per-column counts and the first rows; `locators_file` has every row, always (bounded at 2 GiB, said). No hash, digest or fragment of a value is written anywhere, and a database, table or column name shaped like a token is withheld from every printed channel (the network pack's withholding block, now also in this tool, byte for byte; the test that holds the copies equal covers it).

There is no `sql` in this mode on purpose: a `WHERE` or `LIKE` over a column whose values are withheld would confirm a guess, one call at a time, so the mode exports whole rows, reads them from the table itself (`NOT INDEXED`) in the table's own order, never in an index's (whose order is the indexed values'), and takes no filter; `n_ranks` names the columns whose values that order follows. What locates a row is said as `table_kind`. On an ordinary rowid table it is the `rowid`, SQLite's row key, which is no column's value unless the application set it, and `rowid_from`/`rowid_to` select by it. On a table whose one primary key column is declared `INTEGER` (and kept in no index of its own: `INTEGER PRIMARY KEY DESC` is not an alias), that column is the rowid, so the rowid is a value: it is never printed, a range is refused (`rowid_is_a_value`), and rows are located by their position `n`, which ranks the key's values. A WITHOUT ROWID table is recognised by SQLite's own `PRAGMA table_list` (or the statement's words where that pragma is missing), whatever its columns are named, and is read `ORDER BY` its whole primary key with the key's collations and directions, since SQLite otherwise reads it through a covering index in another column's order: `n` ranks the key's values. A rowid table whose columns named `rowid`, `oid` and `_rowid_` hide the rowid is `shadowed` (`n`, in rowid order, or ordered by its `INTEGER PRIMARY KEY`). A virtual table is located by `n` in its module's order, which can be a value's (fts5vocab returns its terms sorted); where its module cannot start under the read-only authorizer (fts5 on Debian's SQLite 3.40) the answer is the named state `virtual_table_unsupported`. An integer's length is the characters of its decimal form, so it tells its order of magnitude; a real's is its shortest repr, which does not (`1e+20` is `real:5`).

Nothing of a reading error is printed in this mode but what its code decides: sqlite's message can quote a value (a generated column's `json_extract` quotes the value it failed on), and so can the class Python gives the error (a message that quotes bytes that are not UTF-8 arrives as a `UnicodeDecodeError`). Every decision (the time budget, the authorizer, a value over the length limit) is taken on sqlite's result code, and on Python before 3.11, which gives none, on the text before the message's first quote matched whole against sqlite's fixed messages; the answer says the row, and the class and the message go to the values file. A row that cannot be read whole is read alone, and when that fails too a cell at a time: each cell is tried alone, then every readable cell is read in one query under the same order and `LIMIT 1 OFFSET n`, so an exported row's cells are always one row's, and the row is charged once against the limit of rows read so. A cell over the 64 MiB length limit (`value_too_large`) or one SQLite cannot compute (`unreadable`) is listed in `cells_not_exported` and the rest is exported; a row none of whose cells can be read stops the export (`row_unreadable`). Which cells are unreadable follows from the table's own expressions over its values, which the skill says. A write that fails (a full disk) ends the export as JSON with `ok: false`, `reason: values_file_error` and exit 1 (as `network_log_summary` says a read that stopped early), and the counts (`values_file_holds`, `secret_values`, `cells_with_a_value`, which counts only cells that hold a value) are read back from the kept file; a locators file that cannot be written leaves `ok: true` and `complete: false`, and a temporary file that cannot be removed is named. `row_count` N means rows 1..N are in the locators file. Outside a job the request is refused as JSON before anything is opened; the ordinary mode is unchanged but for its own decisions, which now read the code too. `data/sqlite-secrets` says all of this and keeps the locator-column query as the fallback outside a job; `data/sqlite` cites a row's locator, not its `rowid`; `docs/packs.md` states the rule for every tool that takes a filter. The tool-library copy is updated with it. Pack `computer-forensics-base`.
