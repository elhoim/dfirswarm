### Fixed: archive_probe, crypto_id and recovery_key_scan are bounded, stop cleanly, print less of the evidence and carry status (encrypted-containers)

An independent review of the three Phase-1 tools found two bounds that did not hold, a key file printed whole, names and header text printed raw, and no clean stop. Each is fixed at its cause and has a test that fails on the tools as they were.

- **`archive_probe`: `max_metadata_bytes` held for every ZIP.** The tool followed a Zip64 locator only when the End record held the 0xFFFF markers, while Python's `zipfile` follows it whenever it is there, so a file whose End record said "1 entry, 47 bytes" and whose Zip64 record said 3,000,000 passed the check and was then loaded whole: 141 MB took 19.6 s of CPU and 1,107 MB of memory (8 bytes of memory per byte of file). The Zip64 record is read wherever a locator is (as `zipfile` reads it), a directory declared over the bound, over the file, or with more entries than the bound holds is not listed (`not attempted`, `partial`), and the directory is now read by the tool itself in blocks of 1 MiB, so memory no longer follows its size: the same file answers in 0.1 s and 24 MB; a 600,000-entry directory inside the bound lists in 9 s and 50 MB. Because the tool reads the entries itself, one member name that is not valid UTF-8 no longer fails the whole listing (`listing: failed`, which hid which members were encrypted): the name is shown escaped and the others are listed; a directory that breaks off part way is listed as far as it goes (`listing: partial`). ZIP dispatch no longer asks `zipfile.is_zipfile` at all (a signature or an End record decides).
- **`recovery_key_scan`: a clock, and a scan that is not slow.** There was none: at 19.7 MB/s the 600 s limit was reached at about 12 GB, and a kill left no answer, no coverage and a half-written values file. The tool has `max_seconds` (default 480, 1 to 540) and stops at it and on SIGTERM, SIGINT and SIGHUP: it finishes its pages, closes the values file (whole rows only), and prints one answer, `partial`, `interrupted`, that names every file it did not read, every entry of a directory it did not look at and every directory it did not enter (`coverage.entries_not_started`, `directories_not_entered`, `files_stopped`), exit 128 + the signal. If it cannot finish within five seconds of a signal (a read that never returns) the stop is hard: the temporary files go and a short `interrupted` answer is printed. The scan searches for the dash that follows a group instead of trying every byte with a look-behind, and finds exactly what the patterns found (1,000 differential cases and 400 more in the test, 0 differences, including windows that split a value): 537 MB of random data took 27.6 s of CPU and takes 0.6 s.
- **`crypto_id` prints no raw bytes.** `include_head_hex` printed the first 32 bytes of the file, a usual key file size, whole in the answer; the parameter is gone and a call that passes it is refused with that said. The header's text was printed raw although the manifest and three skills said it printed none: the LUKS cipher, mode and hash are now printed only from the closed lists of the names cryptsetup and the kernel use, the UUID only in the UUID form, anything else as `<unrecognised header text withheld>` (`header_fields_withheld` names the field), and the LUKS2 label and subsystem, which are free text, through the names rule below. The claim in the manifest and the skills is corrected.
- **`recovery_key_scan` echoed up to 4 MiB of file text per finding as the private key's "type"** (six such files: 18.9 MB of output). The PEM header is matched as at most two capital words of 2 to 10 letters before `PRIVATE KEY`, and the type is reported from RSA, EC, DSA, OPENSSH, ENCRYPTED, PGP, none, or `other`: the header's own text is never echoed.
- **Names, paths and header strings were printed raw** (a recovery-password-shaped member name 100 of 100, an AWS key id and `password=` too, in `archive_probe`; the same classes in a path component of `recovery_key_scan`, whose identifier rule missed 12-digit numbers, 24 letters, grouped ids, 7-character ids and full-width ids). The three tools share a `NAMES` block (and the network pack's `WITHHOLDING` block, copied byte for byte, for the token shapes): every path and member name is judged component by component, every header string and diagnostic as text, and the part that is shaped like an identifier or a secret is replaced by a fixed marker (`<identifier-shaped text withheld>`, `<secret-shaped text withheld>`, `<recovery-password-shaped name withheld>`), with no length and no fragment; the rest of the name stays. A second check, written apart from the first (eight groups of six digits, a PEM marker, a named secret, vendor prefixes, long hexadecimal or letter-digit-flipping runs), reads every string of an answer and of every row of a paging file once more, replaces what the first let through, and makes the answer `partial`; a test removes the first layer and shows it holds. This covers the member names and 7z header strings and diagnostics of `archive_probe` and its `path`, `crypto_id`'s `path` and header text, and the `file`/`path` fields of `recovery_key_scan`.
  - **What the rule withholds, measured** on 2,000 random draws per shape planted as `docs/<id>.txt` (the test: 300 per shape in each of five slots, whole name, directory, middle of a name, free text): 0 printed of UUIDs, hexadecimal ids of 16, 32 and 64, numbers of 10 digits or more (12 and 20), a recovery password with dashes, spaces, dots, underscores or no separator, AWS access key ids, `password=` and `api_key:` assignments, user-info, groups of four capitals and digits joined by `-` or `.`, mixed-case letters and digits of 8, 12 and 40, full-width ids; printed: mixed-case letters and digits of 9 characters 1.4% and of 16 0.6%, lowercase letters and digits of 8 characters 7.2%, 12 2.4%, 16 0.4%, 24 random letters 2.0%, a 16-character base32 id 3.4%, four groups of four lowercase hexadecimal digits joined by underscores 8.3%. **Not recognised, by design, and asserted:** an identifier of 7 characters or fewer, a number of 9 digits or fewer, a lowercase-only run of up to 22 letters (it reads as a word), a secret of any other shape. Withholding is by shape: a secret of another shape is printed, and a file whose secrets matter is read in a job run with `secret_output: true`.
  - **What it costs an examiner:** names that are not secrets lose a part. Of 137,808 file names of a documents tree 6.9% have a part withheld (10-digit timestamps, UUIDs, hash-named files) and 0.6% of its 17,408 directories; of an application tree 15.8% and 3.1% (a word with a digit inside, such as `libmp3lame`, is withheld in part; `System32` and a few such Windows names are let through). The identifier rule is the interim one of the review (NFKC first, a digit-only run counts from 10 digits, a letters-only run counts unless it reads as words); the shared-block work decides the final one.
- **One answer, whatever stops the tool.** All three stop on SIGTERM, SIGINT and SIGHUP with one JSON answer and exit 128 + the signal (they were empty, exit -15/-2/-1, a traceback for SIGINT); `archive_probe` ends the 7z it started (it survived a SIGTERM and a SIGKILL of the tool) with the shared process block of the network pack (a parent-death signal on Linux, the process tree killed on a signal or at `max_seconds`); no temporary file of a paging file is left in `$OUT` on any exit; a file the tool cannot read is an error answer, not a traceback (`crypto_id` and `archive_probe` on an unreadable file); a directory as the path says "is a directory". `archive_probe` has `max_seconds` (default 100, below the 120 s timeout): it ends the 7z and says what was not read.
- **Every answer carries `status` and `status_basis`**, errors included (`complete`, `partial`, `failed`; `interrupted` for a stop): all three had none.
- **Paging files are written as the other fixed packs write them:** a result file that is there is never replaced (a rerun with other limits, or one the clock stopped, takes the next free name and the earlier, larger file is kept byte for byte), and a file name that is not UTF-8 no longer stops `recovery_key_scan` with a `UnicodeEncodeError` on Linux (paging and values file are ASCII JSON; the values file is written one row per write).
- Tool versions: `archive_probe` 3, `crypto_id` 3, `recovery_key_scan` 4 (the parsers `archive_probe/3`, `crypto_id/3`, `recovery_key_scan/3`); pack 1.6.0. The pack's goal reads "the hash of the unlocked image (a hash of evidence, not of a secret)".
- Tests: `tests/pack-encrypted-containers-fixes.test.ts` (every finding, on the Zip64 fixtures built from the APPNOTE layouts, a stand-in `7z` that waits, a clock that runs fast and a file system that reads slowly) and `tests/pack-encrypted-containers-names.test.ts` (the blocks byte for byte, 300 draws per shape in five slots with the rates above asserted, the shapes that are printed asserted, every regular expression of the blocks timed on 4,096 and 32,768 adversarial characters, the output check with the first layer removed).
- Not done here (see the review): the ZIP flags of the local headers are not compared with the central directory's (a cost of one read per member); the PDF and OLE search maps the whole file and has no partial answer past the clock beyond the markers found so far; the p7zip 16.02 listing format was not available to check. `encrypted_survey` and `ransom_note_scan` (ransomware-response) are another pull request's.
