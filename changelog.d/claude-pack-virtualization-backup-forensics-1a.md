### Added: the virtualization-backup-forensics pack, first part: three tools and the skills that name them

A thirteenth pack for the part of a case that sits above the guest: what the hypervisor's management records and VM configuration files say, whether a disk or snapshot chain is whole, what a backup system's catalogue, job record and retention setting show, and which recovery points survive. It reads exports and files offline; it never runs hypervisor or backup software, reads no guest content, reaches no live system, and says plainly which products it cannot read. It depends on `computer-forensics-base` (which declares `qemu-img` and Dissect as optional programs) and adds no program of its own. This change carries the pack, its three tools and one skill for each; the router, the method leaves, the recovery skills and the goal template follow in the next change.

- **`virtualization_inventory`** lists the VMs, disk files, snapshots and datastores that VMware `.vmx`, `.vmsd` and `vmInventory.xml`, libvirt domain, snapshot and pool XML, and Proxmox VM configurations and `storage.cfg` name, with the file and the line or XML element of each statement. Hyper-V, VirtualBox and OVF files are recognised and listed as unsupported. A disk is looked up only among the files given (`in_set: no` is a statement about the set), a hypervisor storage volume is listed and not looked up, a Proxmox `[special:...]` section (such as the cloud-init settings) is listed as special and not as a snapshot, and the keys that look like credentials (a console password, a cloud-init password, an SSH key, a user-data blob) are named with their line, their section and the length of the value, in every section they sit in, and never shown; a libvirt console password attribute is named up to 200 times and counted past that. A Proxmox configuration names its first 200 snapshot and special sections with their totals (every snapshot section is also a row of `snapshots`, paged whole), and an XML file in an encoding the reader does not know fails that file while the run goes on. A Proxmox volume `storage:volume` is judged whole before it is split, so a secret that spans the `:` withholds both pieces.
- **`snapshot_chain_check`** reads VMDK descriptors (text or embedded in a sparse extent), VHD, VHDX and QCOW2 headers and the disk names in `.vmx` and `.vmsd`, and reports each disk, parent edge, descriptor extent and chain with its identity check: a VMDK CID as the 1 to 8 hexadecimal digits a writer prints, compared as a number; a VHD parent unique id; a VHDX child's `parent_linkage` held against the parent's DataWriteGuid (the field MS-VHDX says it records; the virtual disk id is shown as information); QCOW2 records no identity of its backing file and says so, and a raw backing file is a base that is present and not read. A chain is `complete` only when every parent is in the set and read, the identities agree where recorded, and every extent and external data file is present; otherwise its status names the first problem from the leaf (`cycle`, `too_deep`, `broken`, `parent_unreadable`, `identity_not_compared`, `identity_mismatch`, `extent_missing`, `data_file_missing`) and `issues` lists each kind found. Chains are found in one memoised pass with the clock checked throughout (the reading stops at four fifths of `max_seconds`, and writing the rows and the answer stops at `max_seconds` itself), and a cycle no leaf reaches has a row of its own. Markers (an unclean-close flag, a QCOW2 dirty bit, a VHDX log GUID, a leftover delta no snapshot or configuration names, a running disk that is a delta while the snapshot database lists none, a lock artefact, a sparse extent no descriptor names, two descriptors with one CID, parent names that disagree, an absent external data file) are candidates with the observation beside them, never verdicts. A name inside a file is looked up among the files given and never opened by the tool. `qemu-img` runs only when asked (`qemu_img: auto` or `require`), once per image of the set with the format fixed and never with `--backing-chain`; a VMDK text descriptor, an extent another descriptor names and a QCOW2 image with an external data file are not given to it (it would open the files they name), and a run that fails or times out makes the answer partial. A `.vmx` or `.vmsd` over 16 MiB is named and not read, and a QCOW2 snapshot table read short of its declared count is partial. A header that fails its own check (a VHD footer or dynamic-header checksum, both VHDX headers' or both region tables' CRC-32C; of the two region-table copies the first that holds is read) is read as written, named by a marker and makes the answer partial, and so does a chain the `max_chain_depth` limit stopped (the answer names the limit and never says every limit held); one VHDX header that fails its signature or CRC-32C (marker `vhdx_header_copy_damaged`; the other is taken as current) and a VHD whose end footer is missing (marker `vhd_footer_copy_missing`; the start copy is read) are named by a marker and make the answer partial too. A QCOW2 child that declares a qcow2 backing format over a raw file is `parent_unreadable`, and the chain note says so.
- **`backup_audit_normalise`** turns the Proxmox VE and Proxmox Backup Server task index (both UPID layouts: the Backup Server's carries a task counter and an escaped worker id) and Proxmox VE task logs, or a CSV, JSON Lines or XML export of any product read through a mapping the caller declares (which field is the time, the action, the result, the actor and the object, how the time is written, what each action means), into canonical events with their file, line or record and byte offset. A product with no fixtures here (Veeam, Commvault, Rubrik, Cohesity, Acronis, NetBackup, vCenter and others) is refused by name when asked for with `format: auto`, and no vendor layout is guessed. A time with no zone is not assumed to be UTC, and a time that does not match its declared format says so in a fixed phrase. A declared field a JSON Lines or XML record does not have is counted per field, and a time or action absent, or a declared time that never parses under the `time_format` given, makes the answer partial. A declared XML record is held one at a time and bounded to 4 MiB of text and attributes (a record over it is counted and located, never read in part); one XML file that cannot be read, an encoding the reader does not know included, fails that file and the run goes on, and a file's state is set by its own errors. A Backup Server status `unknown` is the result unknown (this tool's mapping of that word), and the worker id is withheld in both its forms (as written and unescaped) whenever either form is.
- **For all three:** standard library only; every answer carries `status` and `status_basis`; every list is paged and the whole is kept in a file the answer names; every limit is reported (files, depth, entries, snapshots, chain length, line length, XML elements, depth and record bytes, distinct values, time); XML is read with every DOCTYPE and entity declaration refused; in a job only `$OUT` is written. Every key and value of an answer, an error answer and a paging-file row passes one way out (a block the three tools carry byte for byte) when it is written, and what it shows is decided by the field it fills, in three layers. **(1) An allow-list for identifier-shaped fields.** A name (VM, datastore, snapshot, storage, key), a path or file name (judged component by component), an identifier of a known kind (GUID, VMFS volume id, `naa.`, `eui.`, `t10.` and `wwn-` device ids, VMware uuid, MAC, CID, number) and a simple value (an enum word, a version, a time) is shown only when it fits the plain grammar of its kind: letters, digits, space and `. _ - ( ) + [ ] ' # , & ~ % $` (a path adds `/`, `\` and a drive, storage or `host:port` prefix), no `=` or `@`, a `:` only between digits (or in an id), at most 160 characters, no known token prefix, no secret's name beside a random-looking piece, no invisible character, and no run of 16 or more letters and digits that changes class as random text does unless it is words, a date or a well-formed id; anything else is `<withheld: N bytes, field F>`, with the original in the 0600 values file when `write_text` is on in a job. **(2) A deny-list for every other string** (a host name, a description, an annotation, an audit action or actor, a message, any text the tool wrote around a name), judged on a copy from which the characters of the Unicode categories Cf, Cc, Mn, Me, Cs, Co, Cn, Zl and Zp, the Hangul fillers and the escapes of such characters are taken out (so a token split by bidi isolates, variation selectors, tag characters, combining marks or `⁦` is a token), folded to NFKC, with `\xNN` escapes of printable characters decoded: user-info runs to the last `@` before the host; the shared block's token rules (with a reverse character scan in place of its quadratic grow loop) and the shapes added here (a base64 key with or without padding, a slashed run, the head of a prefixed token in any case, a PEM key, a run of more than 18 digits) run on the same text and what any of them finds is withheld as one run; and the value after a name that says it is a secret is found anywhere in the string, secret word first (password, passwd, passphrase, pwd, secret, token, credential, api, access, account, private, master, shared, signing and encryption key, pass, pw, auth, sig, sas; any case, glued to what precedes it or in CamelCase, with quotes and escaped quotes), in time linear in the length. **(3) A check written apart from the two above** (its own normaliser, named-secret search, class-transition test and base64 and hexadecimal rules; none is reused) reads the serialised text back; a string it finds suspect is replaced by `<withheld: N bytes>`, its place and the check that fired are listed in `boundary.replaced_at`, and the answer becomes partial. The judging of one run shares `max_seconds` (plus a short grace for the final answer) and a cap of 400 million characters, and a string over 256 KiB is judged in its first 256 KiB: past either limit a string not judged before is withheld by its size, the answer is partial and `boundary.stopped_by` names the stop. Shown as they are: the exact names of the files the run made (registered as each is created, never a pattern) and a VMDK create type. A lone surrogate in a value no longer fails the run; SIGTERM, SIGINT and SIGHUP end the tool with one JSON answer that names the signal and any paging file it leaves (kept as `<name>.partial`, never a temporary file nothing names, also when the signal comes while a write is in progress or while the file is being made) and exit 128 plus the signal. A file's extension is shown only when it is 1 to 10 letters or digits; any other is counted under `(other extensions)`. The originals go to one 0600 file only with `write_text: true` in a job.
- **What the examiner loses.** On 100,000 realistic strings that are not secrets (52 classes, seeds 11 and 77: host names, VM, snapshot and file names in CamelCase, long, hyphenated and non-ASCII forms, Veeam and VMware snapshot names, ESXi `/vmfs/volumes/<id>/` paths, Windows and Linux paths, `naa.`/`eui.`/`t10.`/`wwn-` ids, `ddb.longContentID`, GUIDs, VMware uuids, MACs, `iqn` names, Proxmox volumes and backup ids, versions, times, Kubernetes names, free text), the share the way out changes falls from 22.6% to 12.8% overall and, in the fields the allow-list judges, from 14.7% to 0.57% by field type: identifiers 16.7% to 0 (the `naa.` ids and `ddb.longContentID` that were 100% withheld are readable), paths 28.1% to 0.01% (ESXi paths 94% to 0.05%, `t10.` ids 88% to 0.05%, paths with spaces 50% to 0), simple values 0 to 0, names 4.1% to 2.3% (all but 0.1% of it Kubernetes pod names with a random hash, 21% of them). Free text is unchanged by design (42.8%, the share of the generated classes that are secret-shaped by construction: hexadecimal digests and base64 of words, 100% and 42% of their classes) and the hosts of the E1a corpus (random-looking C2 domains 36% against 21% before) stay on the deny-list. The second check fired on 0 of 100,000 sealed strings with one seed and 1 with the other, where it fired on 1 in 99,996 before.
- **Skills:** `hypervisor/inventory`, `snapshots/chain-integrity` and `backup/catalogues-and-retention`, each within the 800-token budget (`backup/catalogues-and-retention` says that a CSV header without a declared column fails the file and that a time that never parses makes the answer partial; the leaves' Sensitive output lines follow in the next change).
- **Limits worth knowing.** The layouts are implemented from the formats' public descriptions and checked against synthetic files and, where a host has one, against files a real `qemu-img` made (qcow2 chains of depth 1, 3 and 10 and one on a raw base, VMDK monolithicSparse chains, twoGbMaxExtentSparse, VHD and VHDX; 7.2 here); VHD differencing disks and VHDX parent locators are checked against synthetic files only, because that `qemu-img` cannot make them. They have not been checked against files every product and version writes, and no Proxmox Backup Server task file from a real host is among the fixtures (the UPID layout is written from its published format). The checks are heuristics, which is why the skills say to run as a job with `secret_output: true`. Measured on 5,000 fresh random plants of each of 175 shapes in each of three places (alone in a name field, as a path component, in free text), in each of the three tools (the figures are the worst of the three tools and the three places; the 95% Wilson bound on 0 of 5,000 is 0.08%): **not shown in any tool or place** (0 of 5,000): `ghp_`, `github_pat_`, `xoxb-`, `glpat-`, `sk-`, `sk-proj-`, `sk_live_`, `SG.`, `AIza`, `npm_` and `AKIA` tokens (the lower-cased `akia` too), JWTs (also inside a path), PEM keys, 40- and 64-digit hexadecimal, user-info in every written form (URL, bare, after `storage:`, an `@` inside the password, a `%5C` user, scheme-less), the value after any of 27 secret names glued to a letter or in CamelCase (`vncPassword=`, `adminPassword=`, `accessToken:`, `SecretAccessKey:`, `PWD=`, `pass=`, `pw=`, `credential=`, `auth=`, `PGPASSWORD=`, `MYSQL_PWD=`, `sig=`, `cipassword:`, `--password x` and the rest; values of 8, 14 and 24 characters), `AccountKey=`, a padded 16-, 20- or 32-byte base64 key, and a `ghp_`, `AKIA` or AWS-style token split at random points by any of 15 invisible or formatting characters (bidi isolates, variation selectors, tag characters, combining marks, fillers, zero-width, soft hyphen, BOM and others; 0.02 to 0.04% for the 40-character key). **Shown at a rate:** an AWS-style 40-character secret key 0.02 to 0.08% (0.2% when it holds two `/` in a path); a 24-character base64 key with a `/` 0.7% in a path; a 16-byte base64 key without padding (22 characters) 0.2% in a name, 3.2% in free text, 5.6% in a path; the same 20-byte key 0.3 to 1.1%; a padded 16-byte key followed directly by a letter 14% in free text (0 in a name or a path); a uniform random string with nothing before it: under 16 characters all, 16 characters 21 to 100% by alphabet, 20 characters 0.9 to 1.7% for letters and digits and 7 to 10% for one case of letters, 24 characters 0.4 to 0.7% and 3 to 5%, 32 characters 0.2% and about 1%, 44 characters at most 0.3%; hexadecimal under 32 digits in free text (20 digits 20%, 24 digits 12%; 32 or more is withheld). Measured again through each tool's own code and its real fields (three fields per tool, 5,000 fresh plants per field, 37 shapes, the shipped tool run as a process with only a JSON request): 26 of the 37 shapes shown in 0 of 5,000 in every field (upper bound 0.08%), and for the rest an AWS-style key at most 0.08%, a split AWS key 0.02%, a 32-character random string after `Bearer ` 0.04%, a 32-character URL-safe base64 string at most 0.14%, a 24-character base64 string 0.3 to 2.9%, an unpadded 20-byte key 0.2 to 1.4% and an unpadded 16-byte key 0.6 to 4.8%; the second check replaced 2,251, 2,911 and 15,348 strings in those runs in the chain, inventory and audit tools, and that is where most of the 16- to 24-character strings stopped. **Not recognised at all:** a plain password or passphrase alone in a name, pronounceable text, a UUID-shaped secret (a GUID is a readable id by design), anything under 16 characters, a token split across two fields, a field a format ends at a NUL (a VMDK descriptor line, a VHD parent name, an embedded descriptor) whose piece before the NUL is under 16 characters, and a secret in another encoding. Version and vendor facts are not stated.

the stop, the cap and the answer's grace; a lone surrogate in a JSON Lines value, a SIGTERM that names its paging file, a declared time that never parses, the VHDX and VHD markers, the qcow2-over-raw note and the original in the values file), `-canary` (with `-canary-audit-1` to `-4`, `-canary-backstop` and `-canary-backstop-audit`, which share `-canary-lib.ts` and are split so that no file nears the 300 s the runner allows one; For this change the structure-aware fuzz ran 5,000 cases per tool on macOS with Python 3.12 and again with 3.14 (seeds 8001 and 8002: 10,695, 26,555 and 77,150 planted secrets, none shown; every answer the tool's own JSON), 1,500 per tool in a Linux container (one CPU, `--init`, Python 3.11, qemu-img 7.2) and four earlier seeds of 1,500 per tool that found the defects fixed here; real `qemu-img` made chains of depth 1, 3 and 10 (qcow2 and VMDK chains of 2, 4 and 11 disks read as complete with and without `qemu_img: auto`; vpc and vhdx standalone). No traceback, no answer that is not JSON, no exit code that disagrees with the status, nothing written outside the output directory, and no secret of a shape the layers claim shown; what was shown is listed under the limits above. `docs/packs.md` and `README.md` carry the pack's row.
