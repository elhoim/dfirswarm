### Added: the virtualization-backup-forensics pack, first part: three tools and the skills that name them

A thirteenth pack for the part of a case that sits above the guest: what the hypervisor's management records and VM configuration files say, whether a disk or snapshot chain is whole, what a backup system's catalogue, job record and retention setting show, and which recovery points survive. It reads exports and files offline; it never runs hypervisor or backup software, reads no guest content, reaches no live system, and says plainly which products it cannot read. It depends on `computer-forensics-base` (which declares `qemu-img` and Dissect as optional programs) and adds no program of its own. This change carries the pack, its three tools and one skill for each; the router, the method leaves, the recovery skills and the goal template follow in the next change.

- **`virtualization_inventory`** lists the VMs, disk files, snapshots and datastores that VMware `.vmx`, `.vmsd` and `vmInventory.xml`, libvirt domain, snapshot and pool XML, and Proxmox VM configurations and `storage.cfg` name, with the file and the line or XML element of each statement. Hyper-V, VirtualBox and OVF files are recognised and listed as unsupported. A disk is looked up only among the files given (`in_set: no` is a statement about the set), a hypervisor storage volume is listed and not looked up, a Proxmox `[special:...]` section (such as the cloud-init settings) is listed as special and not as a snapshot, and the keys that look like credentials (a console password, a cloud-init password, an SSH key, a user-data blob) are named with their line, their section and the length of the value, in every section they sit in, and never shown; a libvirt console password attribute is named up to 200 times and counted past that.
- **`snapshot_chain_check`** reads VMDK descriptors (text or embedded in a sparse extent), VHD, VHDX and QCOW2 headers and the disk names in `.vmx` and `.vmsd`, and reports each disk, parent edge, descriptor extent and chain with its identity check: a VMDK CID as the 1 to 8 hexadecimal digits a writer prints, compared as a number; a VHD parent unique id; a VHDX child's `parent_linkage` held against the parent's DataWriteGuid (the field MS-VHDX says it records; the virtual disk id is shown as information); QCOW2 records no identity of its backing file and says so, and a raw backing file is a base that is present and not read. A chain is `complete` only when every parent is in the set and read, the identities agree where recorded, and every extent and external data file is present; otherwise its status names the first problem from the leaf (`cycle`, `too_deep`, `broken`, `parent_unreadable`, `identity_not_compared`, `identity_mismatch`, `extent_missing`, `data_file_missing`) and `issues` lists each kind found. Chains are found in one memoised pass with the clock checked throughout (the reading stops at four fifths of `max_seconds`, and writing the rows and the answer stops at `max_seconds` itself), and a cycle no leaf reaches has a row of its own. Markers (an unclean-close flag, a QCOW2 dirty bit, a VHDX log GUID, a leftover delta no snapshot or configuration names, a running disk that is a delta while the snapshot database lists none, a lock artefact, a sparse extent no descriptor names, two descriptors with one CID, parent names that disagree, an absent external data file) are candidates with the observation beside them, never verdicts. A name inside a file is looked up among the files given and never opened by the tool. `qemu-img` runs only when asked (`qemu_img: auto` or `require`), once per image of the set with the format fixed and never with `--backing-chain`; a VMDK text descriptor, an extent another descriptor names and a QCOW2 image with an external data file are not given to it (it would open the files they name), and a run that fails or times out makes the answer partial. A `.vmx` or `.vmsd` over 16 MiB is named and not read, and a QCOW2 snapshot table read short of its declared count is partial.
- **`backup_audit_normalise`** turns the Proxmox VE and Proxmox Backup Server task index (both UPID layouts: the Backup Server's carries a task counter and an escaped worker id) and Proxmox VE task logs, or a CSV, JSON Lines or XML export of any product read through a mapping the caller declares (which field is the time, the action, the result, the actor and the object, how the time is written, what each action means), into canonical events with their file, line or record and byte offset. A product with no fixtures here (Veeam, Commvault, Rubrik, Cohesity, Acronis, NetBackup, vCenter and others) is refused by name when asked for with `format: auto`, and no vendor layout is guessed. A time with no zone is not assumed to be UTC, and a time that does not match its declared format says so in a fixed phrase. A declared field a JSON Lines or XML record does not have is counted per field, and a time or action absent makes the answer partial. A declared XML record is held one at a time and bounded to 4 MiB of text and attributes (a record over it is counted and located, never read in part).
- **For all three:** standard library only; every answer carries `status` and `status_basis`; every list is paged and the whole is kept in a file the answer names; every limit is reported (files, depth, entries, snapshots, chain length, line length, XML elements, depth and record bytes, distinct values, time); XML is read with every DOCTYPE and entity declaration refused; in a job only `$OUT` is written. A name or value that looks like a token, a key or user-info is withheld by the block the network pack's tools carry, byte for byte, and then again at one way out that every key and value of an answer, an error answer and a paging-file row passes when it is written: the whole string is checked before anything cuts or folds it, with the shapes that block leaves alone added (user-info after `:` or `/`, as in a Proxmox `storage:user:password@host`; a 16-byte base64 key with `/`; a secret key with one `/`; a token's head), and the written text is read back and checked with the same rules, so that a string that slipped through is replaced by `<withheld: N bytes>` and the answer becomes partial. A file's extension is shown only when it is 1 to 10 letters or digits; any other is counted under `(other extensions)`. The originals go to one 0600 file only with `write_text: true` in a job.
- **Skills:** `hypervisor/inventory`, `snapshots/chain-integrity` and `backup/catalogues-and-retention`, each within the 800-token budget (the largest, `snapshots/chain-integrity`, is 781).
- **Limits worth knowing.** The layouts are implemented from the formats' public descriptions and checked against synthetic files and, where a host has one, against files a real `qemu-img` made (qcow2 chains of depth 1, 3 and 10 and one on a raw base, VMDK monolithicSparse chains, twoGbMaxExtentSparse, VHD and VHDX; 7.2 here); VHD differencing disks and VHDX parent locators are checked against synthetic files only, because that `qemu-img` cannot make them. They have not been checked against files every product and version writes, and no Proxmox Backup Server task file from a real host is among the fixtures (the UPID layout is written from its published format). The shape check is a heuristic: a secret that does not look like a token (a short password) is not recognised, which is why the skills say to run as a job with `secret_output: true`. Version and vendor facts are not stated.
- **Tests.** `tests/pack-virtualization-chain.test.ts`, `-inventory`, `-audit` (with a regression test for each fix the review asked for), `-shared` (the shared blocks held equal to each other and to the network pack's withholding and process blocks, the manifests held to the scripts, only `$OUT` written in a job), `-canary` (20 canary shapes planted in every slot of every format, each tool run in and out of a job with a page of one row and of two hundred; stdout, stderr, every file written and every file name searched for any twelve characters of each secret, its base64 and its digests; and the backstop shown by removing the seal on purpose) and `-fuzz` (a seeded mutation fuzz, 120 mutants per tool by default), with the builders in `tests/pack-virtualization-harness.ts`, and the pack's own `tests/pack.test.sh`. A structure-aware fuzz of 5,200 cases per tool on macOS (Python 3.12 and 3.14) and 1,500 per tool in a Linux container (one CPU, Python 3.11, qemu-img 7.2) was run for this change. `docs/packs.md` and `README.md` carry the pack's row.
