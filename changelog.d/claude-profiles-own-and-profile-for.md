### Added: image profiles for the macOS, cloud and triage packs and for the base pack alone (`core`); `profile-for` chooses by membership first

A macOS case rode the `mobile` image, and cloud and triage cases rode `full`, the largest one. `images/profiles.json` gains four profiles. Three hold one pack and the base pack: `macos` (macos-forensics), `cloud` (cloud-forensics) and `triage` (triage-collection). The fourth, `core`, holds the base pack (computer-forensics-base) and nothing else: its programs (the Sleuth Kit, plaso, dissect, bulk_extractor and the rest of what that pack names) and no other pack's. `full` is unchanged, `re` still holds the ransomware pack, and `mobile` still holds macos-forensics as the dependency of mobile-forensics (a run with both packs runs them in the one `mobile` image). The images and image-boot workflows build and boot the four new profiles beside the others.

`recipe.py profile-for` now decides in this order: the smallest profile that holds the packs (they and their dependencies are among its packs; `full` holds every pack, so a pack no smaller profile lists gets `full`); for a pack no profile lists, such as an installed pro or third-party pack, the smallest profile that covers the programs and Python packages it names; else `full`. Before, a pack whose tools name nothing beyond the base's was covered by every profile and was given whichever of them had the fewest packs, `memory` among them, even when `full` or another profile held it.

A run of several packs. A profile is now chosen because it holds the run's packs, not because it names the same programs, so a smaller image no longer serves a multi-pack run by chance. `ransomware-response` with `windows-forensics`, with `encrypted-containers` or with `memory-forensics` resolved to `disk`, `disk` and `memory` as the run's default image, and now resolves to `full`: no other profile holds both packs. The jobs of each pack still run in the smallest image that holds it (`re`, `disk`, `memory`). A host that built only `disk` or `memory` needs `full` for these runs, or `--image`. Every other run of one to three packs boots the same set of images as before, except where a pack of the new profiles is named (and the base pack alone, below). The base pack, which every profile holds, may run its jobs in another image of that set than before: in six runs of the frozen table (linux-forensics with memory-forensics, memory-forensics with mobile-forensics, and four larger runs) it ran in `memory` and now runs where most of the run's packs run, then in the profile of the fewest packs, then by name (`linux`, `mobile`, `re`, `disk`); a pair like linux-forensics with memory-forensics boots the same two images. A run of `mobile-forensics` (with `macos-forensics` and the base pack, its dependencies) still boots the one `mobile` image.

The base pack alone. A run whose only pack is `computer-forensics-base` boots `core`, the smallest profile that holds it. It was `memory`, the first of the six two-pack profiles in the order of the file (with Volatility and MemProcFS in it for nothing the run asked for). An unlisted pack that depends on the base pack and names only what the base pack names (a pack of stdlib Python, or one that names only Sleuth Kit programs such as `fls` or `mmls`, with or without that dependency) gets `core` too. A pack that names a program the base pack does not (`vol`, `tshark`, `pwsh`) goes to the smallest profile that names it, and a pack that names programs no profile has together, to `full`: `core` lacks them. A run with no packs at all, or an unlisted pack that names nothing and depends on nothing, still boots `base`, the agents' bare image. When the run's other packs go to `full`, which the base pack does not join, `core` is booted for the base pack's jobs, where `memory` was before, so the number of images a run boots does not grow.

Ties are decided, not left to the order of `images/profiles.json`: of the candidates, `full` last, then the fewest packs, then the fewest programs the profile's packs name, then the profile's name.

Upgrading. A host that built only `full` or `mobile` must build the new profiles for runs of the macOS, cloud and triage packs (`python3 images/recipe.py profile-for PACK...` names the profile), or pass `--image`; the cloud and triage cases rode `full`, the macOS case rode `mobile`. A run of the base pack alone needs `core` (it was `memory`). A pinned images lock (`SWARM_IMAGES_LOCK`, `images/images.lock.json`, a private build repository's `images.lock.json`) needs entries for `core`, `macos`, `cloud` and `triage`: for a profile the lock does not name, the kickoff falls back to the unpinned local name `dfirswarm-<profile>:dev-<arch>` and the run loses the digest pin. `images/README.md` says so under "When the profiles change".

`tests/recipe.test.sh` keeps the rule: every pack under `packs/` is in `full`, every pack resolves to a profile that holds it and is the smallest that does, macos-forensics resolves to `macos`, cloud-forensics to `cloud`, triage-collection to `triage`, the base pack to `core`, no packs to `base` and mobile-forensics to `mobile`; a pack only `full` lists goes to `full` and not to a profile that covers it by chance; unlisted packs go to `core`, `memory`, `network`, `cloud` or `full` as above; the base pack with macos-forensics and mobile-forensics boots one image (`mobile`) and with macos-forensics alone `macos`; the images a run boots, and where the base pack's jobs run, are compared with a table frozen from before this change (the only differences allowed are the new profiles, the three `ransomware-response` pairs above, the base pack alone and the six moves of the base pack's jobs, and no run boots a `core` image but the base pack alone or more images than before); the tie results are pinned and do not change when `profiles.json` is reordered; and the two workflows build exactly the profiles in `profiles.json` (the arm64 entries too, however the file writes them). `images/README.md` and the docs name the new profiles and state the order.
