### Added: image profiles for the macOS, cloud and triage packs; `profile-for` chooses by membership first

A macOS case rode the `mobile` image, and cloud and triage cases rode `full`, the largest one. `images/profiles.json` gains three profiles, each holding one pack and the base pack: `macos` (macos-forensics), `cloud` (cloud-forensics) and `triage` (triage-collection). `full` is unchanged, `re` still holds the ransomware pack, and `mobile` still holds macos-forensics as the dependency of mobile-forensics (a run with both pack runs them in the one `mobile` image). The images and image-boot workflows build and boot the three new profiles beside the others.

`recipe.py profile-for` now decides in this order: the smallest profile that holds the packs (they and their dependencies are among its packs; `full` holds every pack, so a pack no smaller profile lists gets `full`); for a pack no profile lists, such as an installed pro or third-party pack, the smallest profile that covers the programs and Python packages it names; else `full`. Before, a pack whose tools name nothing beyond the base's was covered by every profile and was given whichever of them had the fewest packs, `memory` among them, even when `full` or another profile held it.

A run of several packs. A profile is now chosen because it holds the run's packs, not because it names the same programs, so a smaller image no longer serves a multi-pack run by chance. `ransomware-response` with `windows-forensics`, with `encrypted-containers` or with `memory-forensics` resolved to `disk`, `disk` and `memory` as the run's default image, and now resolves to `full`: no other profile holds both packs. The jobs of each pack still run in the smallest image that holds it (`re`, `disk`, `memory`). A host that built only `disk` or `memory` needs `full` for these runs, or `--image`. Every other run of one to three packs resolves as before, except where a pack of the new profiles is named. A run of `mobile-forensics` (with `macos-forensics` and the base pack, its dependencies) still boots the one `mobile` image: the base pack, every profile's dependency, goes where the run's other packs ended up, as before, and does not keep an image of its own booted for it alone.

Ties are decided, not left to the order of `images/profiles.json`: of the candidates, `full` last, then the fewest packs, then the fewest programs the profile's packs name, then the profile's name. The base pack alone (it names the Sleuth Kit programs, which the `base` image lacks) now resolves to `cloud`, the profile of two packs that names the fewest programs; it was `memory`, the first of the nine profiles that hold it. An unlisted pack of stdlib Python that depends on the base pack gets the same; an unlisted pack that names nothing and depends on nothing gets `base`.

Upgrading. A host that built only `full` or `mobile` must build the new profiles for runs of the macOS, cloud and triage packs (`python3 images/recipe.py profile-for PACK...` names the profile), or pass `--image`; the cloud and triage cases rode `full`, the macOS case rode `mobile`. A pinned images lock (`SWARM_IMAGES_LOCK`, `images/images.lock.json`, a private build repository's `images.lock.json`) needs entries for `macos`, `cloud` and `triage`: for a profile the lock does not name, the kickoff falls back to the unpinned local name `dfirswarm-<profile>:dev-<arch>` and the run loses the digest pin. `images/README.md` says so under "When the profiles change".

`tests/recipe.test.sh` keeps the rule: every pack under `packs/` is in `full`, every pack resolves to a profile that holds it and is the smallest that does, macos-forensics resolves to `macos`, cloud-forensics to `cloud`, triage-collection to `triage` and mobile-forensics to `mobile`, a pack only `full` lists goes to `full` and not to a profile that covers it by chance, the base pack with macos-forensics and mobile-forensics boots one image (`mobile`) and with macos-forensics alone `macos`, the images a run boots are compared with a table frozen from before this change (the only differences allowed are the new profiles, the three `ransomware-response` pairs above and the base pack alone), the tie results are pinned and do not change when `profiles.json` is reordered, and the two workflows build exactly the profiles in `profiles.json` (the arm64 entries too). `images/README.md` and the docs name the new profiles and state the order.
