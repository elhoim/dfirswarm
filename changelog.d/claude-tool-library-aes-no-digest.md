### Security: the two AES key-schedule scanners no longer print or write a digest of a key

`aes_schedule_scan` and `aes_inverse_scan` of the tool library gave each hit `key_sha256` and told the agent that this was what to record in the ledger, and named each key file after the first 16 hex digits of that digest. A digest of a key is a derivable quantity of it, and the rule for every worker is never to write a hash of a secret. A hit now carries the offset, `offset_hex`, `key_bits`, the byte order (and the round order for the inverse layout), the schedule size and `key_file`; the file is still mode 0600, holds the raw key and is the only place the key is. Its name comes from where the key was first found (`key-<offset in hex>-<bits>.bin`, with a number added if the name is taken by anything but a plain file holding this key). The same key found again, at another offset or in a later window or call on the same `out_dir`, names the file it already has: the tool looks through at most 256 `key-*-<bits>.bin` files of that size in `out_dir` for a plain file with exactly the key in it, makes that file private (0600) if it was not, and otherwise writes a new one. A directory, a symlink (even a dangling one, and never followed) or a file of another key at a name is passed over, so a name that can be guessed cannot make a tool fail with a stack trace. The result's note says to record the finding's offset and key file name, never a digest, and the memory pack's `credentials/key-schedules` skill and the library README say the same instead of promising a digest. Both tools' manifest versions go up, and the memory-forensics pack is re-sealed with a new version.

A new test runs both tools outside and inside a job, twice in one directory, over four keys of both sizes (one of them at two offsets), in both byte orders and, for the inverse scanner, both round orders, and asserts that stdout, stderr and every file but the key files hold no 64-hex string, no key in raw, hex or base64 form and no digest of one whole or in part, that no file name carries 16 hex digits or the start of a digest, that a hit has only the listed fields, and that each key file is private and holds exactly one key. It fails on the old code. The only file with the key in it is the key file; the answer was already free of the key itself. Further tests cover a key found in successive windows (one file for it), and a directory, a dangling symlink, a symlink to a file with the key and a loose-mode file of the key at the predictable names.
