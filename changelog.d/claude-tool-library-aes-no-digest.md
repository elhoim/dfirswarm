### Security: the two AES key-schedule scanners no longer print or write a digest of a key

`aes_schedule_scan` and `aes_inverse_scan` of the tool library gave each hit `key_sha256` and told the agent that this was what to record in the ledger, and named each key file after the first 16 hex digits of that digest. A digest of a key is a derivable quantity of it, and the rule for every worker is never to write a hash of a secret. A hit now carries the offset, `offset_hex`, `key_bits`, the byte order (and the round order for the inverse layout), the schedule size and `key_file`; the file is still mode 0600, holds the raw key and is the only place the key is. Its name comes from where the key was first found (`key-<offset in hex>-<bits>.bin`, with a number added if a file of that name from an earlier call holds another key), and the same key found again names the same file. The result's note says to record the finding's offset and key file name, never a digest, and the memory pack's `credentials/key-schedules` skill and the library README say the same instead of promising a digest. Tool versions 1 to 2; memory-forensics pack 1.5.0 to 1.5.1.

A new test runs both tools outside and inside a job, twice in one directory, over four keys of both sizes (one of them at two offsets) in every layout, and asserts that stdout, stderr and every file but the key files hold no 64-hex string, no key in raw, hex or base64 form and no digest of one whole or in part, that no file name carries 16 hex digits or the start of a digest, that a hit has only the listed fields, and that each key file is private and holds exactly one key. It fails on the old code. The tools write the key files only; the answer was already free of the key itself.
