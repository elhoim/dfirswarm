### Fixed: under `--isolation microvm --inputs-copy`, every seat's VM was refused for an evidence mount that allowed execution

A kickoff on 2026-10-05 with `--inputs-copy` failed every seat's VM check with "the evidence can execute in the VM (exec)". The copy (`inputs/` and its pristine clone `.inputs-pristine/`) lives inside the run's directory, which every VM mounts as one read-only share, and only evidence used in place got its own read-only, no-exec share; the VM's probe reads the no-exec flag from the mount that holds the files, so for a copy it read the floor's, which has none, and the kickoff refused the VM, as it should have.

- **The copy is now held exactly like evidence in place.** The kickoff mounts `inputs/` and `.inputs-pristine/` as their own read-only, no-exec shares after the floor, into every seat's VM and the census VM (`scripts/swarm.sh` `inputs_mount_dirs`, the one list of what every VM mounts as evidence: the sets held in place, an attached image, a copy). Job workers already mounted `inputs/` so. The check is not weakened: it passes because the mount that holds the files is no-exec.
- **The probe measures the pristine clone too**, where there is one: `.inputs-pristine/` must be read-only and no-exec in a VM, or the VM is refused. Evidence in place, which has no clone, is unchanged.
- Tests: the probe and verdict units, `tests/microvm-flags.test.sh` (the prepared spec mounts both directories read-only and no-exec, and names no sets for a copy), and the real-VM suite (`npm run test:vm`): a copy-mode VM whose `inputs/` and `.inputs-pristine/` are read-only and no-exec by the guest kernel's mount table, refuse a write, a chmod and a removal, and do not run a file that is executable by its mode and runs when copied off the mount; the in-place case asserts its mount's flags and that nothing is measured for a clone.
