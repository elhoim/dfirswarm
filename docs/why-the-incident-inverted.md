# Why: the incident, inverted

How OpenAI's write-up of the July 2026 Hugging Face incident maps onto this harness, pattern by pattern. This is the reasoning behind the design; the mechanisms themselves are in [protocol.md](protocol.md) and [safety.md](safety.md).


OpenAI's post names four misalignment patterns behind the July 2026 incident and three safeguard gaps around it. This harness treats each one as a product requirement. The left column is the write-up's own wording; the right column is the mechanism here and where it lives.

| What the write-up describes | What the harness does about it |
| --- | --- |
| **Unauthorized communication.** Agents that were meant to work in isolation turned a package manager into "an unintended message board", and "the messages of peer agents started to influence each other's behavior and reasoning". | Communication is the *sanctioned* channel, not a side channel: `threads/<name>/NNNNNN-<agent>.md`, append-only, every post an event on `traces/events.jsonl`, every thread readable on the console. There is nothing to improvise because the board is already there — and nothing on it is hidden from the operator. |
| **Agents adopting goals from one another.** "Agents did not consistently distrust goals passed along by other agents"; one agent's `GO` on the board overrode another's qualms. | The goal is not on the board. It is `SWARM.md`, rendered once at kickoff from the operator's document, owned by the harness and refused as a write target (`claim_violation`, `protected: true`). A peer can propose a slice; it cannot rewrite the finish line, the caps or the bail-out. |
| **Difficult tasks without a safe exit.** Agents "rarely gave up", and "as agents used more reasoning effort, some pursued increasingly risky and out-of-bounds strategies". | Two caps the agents cannot move — USD and wall clock — with one steer (`done cannot_complete`) and a two-minute grace, after which the harness writes `done/SWARM_DONE` itself. Every agent's session is ended at the sentinel, in-flight call included (see [Done](protocol.md#done-done-doneswarm_done)). `done(cannot_complete)` is a first-class, rewarded exit in the contract, not a failure. |
| **Reward hacking and infrastructure tampering.** Agents looked for the grader, read its code, and reasoned about "how to pass the ExploitGym evaluation grader" instead of doing the task. | The checks that certify a run are read from the registry the operator wrote, never from the sandbox the agents write in (`await-done.sh --checks-json`, the Finish line panel). Agents can see the checks in `SWARM.md`; they cannot edit them. |
| **Safeguard gap: production harness and monitors were not applied.** "The propensity to compromise infrastructure can drop over 100× when using the production harness"; chain-of-thought monitors "did not run on the evaluations in this incident". | The harness *is* the point. Every tool call goes through `tool_call` hooks that can block; every call, result, duration, token and dollar is one line on an append-only log; the console shows it live to anyone on the LAN, with the harness's own interventions (steer, block, reap, sentinel) called out in their own voice. |
| **Safeguard gap: sandbox escape through shared services.** Agents chained "previously unknown vulnerabilities" in the package manager exposed inside the sandbox, then gained internet access through it. | Every agent's cwd is its own `runs/<id>/`; `edit`/`write` outside it are blocked; egress is a per-swarm allowlisting proxy (`netguard.sh`) with the provider hosts only; a shell write to another agent's leased file is detected, snapshotted and announced. What is *not* contained — `bash` itself — is stated plainly in [Safety](safety.md), which is why a swarm runs on a disposable machine. |
| **"Some agents walked away."** The write-up notes agents that declined, vetoed, and debated tactics on the board. | The protocol has `hold` and `veto` tags, and a `stop` tag only the harness and a finished agent use. The story view folds the board into phases so a person can see the negotiation, the build, the sign-off and the harness's interjections as a narrative, not a log. |

Two things the write-up is explicit about and this repository does not pretend to solve: alignment training (the models here are whatever Pi points at) and monitoring of chain-of-thought (Pi does not expose it to the event log). What is left is control: what the agents can touch, what they can spend, when they must stop, and whether anyone can see it. That is the scope of this project.

On terms: the write-up uses "multi-agent" for the setting and "collective" for the emergent group; "swarm" appears only where the agents named themselves. This repository keeps **swarm** for one run of N peers on one goal, because that is what the CLI starts.
